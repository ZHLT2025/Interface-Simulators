## 3. 逐项处理

### F02 公网访问安全

**核实事实**
- 5 个端口绑定 `0.0.0.0`，公网可达；Docker DNAT 保留真实源 IP（海外探测节点 IP 出现在容器访问日志中），因此应用层按对端地址做访问控制是有效的。
- `/_sim/*` 管理端点仅靠 Token（明文 HTTP 传输）保护，公网任何地址可尝试。
- `sim-mom` 启动参数含 `--proxy-headers --forwarded-allow-ips *`，任何客户端可用 `X-Forwarded-For` 伪造来源。
- CV 发送器 `target_url` 覆盖无限制，可被用作向任意地址发 POST 的中继。
- MQTT 已有用户名/密码 + ACL；合同端点按客户定义为明文 `http://`、`mqtt://`；凭据均为随机生成的模拟凭据。

**处置（不改变合同协议/报文/字段）**
1. 新增 `simcore/ipguard.py`（最外层中间件）：`/_sim/*` 要求来源 IP ∈ `SIM_ADMIN_ALLOW_CIDRS`（默认回环 + RFC1918，即仅本机/Docker/内网），否则 403；`/_sim/health` 与 `/_sim/cv/evidence/*` 公开；合同端点受可选 `SIM_CLIENT_ALLOW_CIDRS` 控制（默认开放）。
2. `docker-compose.yml`：移除 MOM 的代理头信任参数；所有服务只以 TCP 对端地址判定。
3. `cv/app.py`：`target_url`（emit / emit-raw / 剧本步骤）主机须在白名单（`CV_TARGET_URL` 主机、回环、`CV_PUBLIC_BASE_URL` 主机、`CV_TARGET_ALLOW_HOSTS`），否则 400。
4. `/_sim/status` 输出当前访问控制策略；`.env.example`、使用说明 3.1 节同步。

**验证**（`docs/evidence/f02-external-admin-denied.txt`、`conformance-last-run.txt`）
- 外部节点（es/nl/si、es/il/pl）GET `/_sim/status`、`/_sim/cv/status` → **403**；容器日志记录到各节点真实 IP 被拒。
- 外部节点 GET `/_sim/health` → 200；GET ESB 根路径 → 200；证据路径 → 到达处理器（404 未知 id）。
- `test_mom_ignores_forwarded_headers`：带伪造 `X-Forwarded-For` 的请求，服务端记录的 client 为真实对端。
- `test_cv_target_url_outside_allowlist_rejected`：三种入口均 400。

**保留与限制**
- 合同端点保持明文（客户合同要求），未实施 TLS：本机唯一 IP 证书属 stm-2dmap 且 6 天轮换，且 HTTPS 会改变合同协议；如需传输保护，建议在第四阶段由网络侧（VPN/IP 白名单 `SIM_CLIENT_ALLOW_CIDRS`）解决。
- 管理端点现在只能从服务器本机/内网调用；远程操作者需把出口 CIDR 加入 `SIM_ADMIN_ALLOW_CIDRS`。

### F03 IoT 历史数据与 MQTT 发布

**合同依据**：IF-IOT-003 是 IoT 平台自身存储的设备历史（定义 §20）；IF-IOT-MQTT-001 为 QoS 0、Retain=false 的单向遥测（§23.3），"新订阅端不会收到历史保留消息"（§23.3 注），异常定位表建议"发布无报错但订阅端无消息"时核对 ACL/Topic（§23.6.5）。使用说明 3.3/3.6 亦要求用历史接口做启动基线与缺口补查。即历史存在与否取决于设备数据是否被平台采集，不取决于某个订阅者是否收到。

**实际行为**（`docs/evidence/f03-f04-reproduction.txt`）
- 最近一条 MQTT 消息的每个点位与 IF-IOT-003 LATEST 返回逐一一致。
- Broker 停机 8 秒：发布器 `connected=false`，期间既不采样也不登记历史（最新 serverTime 不变）；恢复后继续，`failed=0`。
- 代码路径：每个采样周期先 `append_history` 再 `publish`（QoS0 无 PUBACK，客户端返回成功即视为已发布，与 §23.6.4-3 一致）。

**结论**：行为符合合同与模拟器职责（模拟"平台已采集"而非"订阅方已收到"），**不修改**。已在差异说明新增 I19 记录该语义；注意事项：Broker 不可达期间历史暂停，这是模拟器建模选择，不代表真实平台行为。

### F04 CV 剧本重复启动

**复现**
- 5 个并发与 20 个同时（Barrier）`run` 请求：均只启动 1 个、其余 409、投递 6 条事件 —— 并行多剧本未复现；但代码上 `running` 由线程自身置位、检查与启动之间无锁，窗口存在。
- `run → stop → 立即 run`：**复现缺陷**。`stop` 立即返回而线程仍在当前步骤（发送中/重试退避中），紧接的 `run` 被 409 拒绝；0.3s 后线程才退出。

**修复**（`cv/app.py`、`cv/pusher.py`）
- `scenario_lock` 串行化 run/stop；新剧本在锁内把 `running=True` 后再 `start()`，并同时检查 `is_alive()`。
- `stop` 置位 `stop_event` 后 `join`（上限 `CV_SCENARIO_STOP_TIMEOUT_SECONDS`=15s），返回 `stopped` 布尔与最终状态。
- `Pusher.send` 接受 `stop_event`：退避等待可被中断，剧本停止时不再卡在重试上（结果记为 `aborted`）。
- 未改动事件结构、生成算法与回放框架。

**验证**：`test_scenario_stop_then_immediate_restart`、`test_scenario_single_instance_under_concurrent_starts` 通过；原 `test_producer_scenario_runs` 回归通过。

### F05 CV 证据 URI 与图片访问

**合同依据**：定义 24.2.1 `evidence.files[].uri` = "证据图片在对象存储或文件服务中的完整 URI"，示例 `oss://cv-evidence/.../frame_001.jpg`；`sha256` = "文件内容 SHA-256 的 64 位小写十六进制"。合同未规定接收方下载图片。

**消费者核实（只读）**：YQYD 接收端 `backend/yqyd/s01/contracts.py` 仅校验 `uri` 等字段存在与 `sha256` 格式，不发起下载。

**三者关系**
| 概念 | 模拟器现状 |
| --- | --- |
| 原始来源引用（报文 `uri`） | 默认 `oss://cv-evidence/{date}/{camera_id}/{event_id}/frame_001.jpg`，与示例一致 |
| 可访问的图片地址 | `GET /_sim/cv/evidence/{event_id}/frame_001.jpg`（公开、不受白名单限制） |
| 实际取得的证据内容 | 真实 JPEG 字节，`sha256(bytes)` == 报文 `sha256`（`test_producer_evidence_sha256_matches_served_image`） |

**结论**：符合合同，**不改代码**。如第三阶段要求报文 URI 可直接下载，设置 `CV_EVIDENCE_URI_TEMPLATE={public_base}/_sim/cv/evidence/{event_id}/frame_001.jpg` 即可。限制：证据图片仅内存保留最近 200 个事件、重启清空；若后续剧本需要长期可取证据，需另行决定是否持久化（本轮不扩展）。
