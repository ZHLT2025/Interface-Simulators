# IOT 接口使用说明书

分册 V1.1｜2026-10-19｜6 项接口

配套定义：[IOT 接口定义](../版本261017/接口定义说明书三、IOT部分-0813.md)。参考：[设备参数表-0805](../../3D数据来源分析/设备参数表-0805.xlsx)、[历史查询模式说明](../../开发说明/IOT接口/IF-IOT-003-查询设备历史数据（单设备）V1.1.md)、[3D 接口定义-1019](../版本261017/接口定义说明书二、3D部分-1019.md)。完整字段与报文查配套定义；建议频率不是提供方承诺，参考开发说明的阶段性采集范围不限制本文的业务闭环。

## 1. 任务范围

- **业务目标：** 取得设备实时及历史参数，支持质量关联分析、设备预警、3D 驱动和融合视觉的工时识别校准，完成业务对象更新及必要的后续操作。
- **本平台角色：** 主动查询设备、参数、历史和推送配置，持续订阅实时数据；只在配置变更时写推送配置。
- **业务输入：** IOT 点位数据，CV 识别的产品台位占用和设备所在台位，MOM 报工匹配的产品信息，以及第三方业务系统的检验、缺陷、返修等质量结果。
- **业务输出：** 产品／台位／设备／有效加工时段及其参数关联，预警结果，3D 更新，以及加工和等待时长等业务结果；采集记录用于追溯，不是流程终点。
- **说明边界：** 本文说明接口在各场景中的用法及处理职责；字段映射、分析算法、预警阈值、工时判断、存储及调度细节由平台业务代码实现，不在本文展开。

| 业务场景 | 接口配合方式与业务结果 |
| --- | --- |
| 加工质量与参数关联分析 | CV 确定产品占用及设备位置，MOM 报工匹配产品，IOT 识别真实有效加工时段；取得该时段参数，关联产品、台位和设备，再结合第三方质量结果进行分析 |
| 设备预警 | 持续接收设备状态和参数；有异常告警字段时转发原生报警，平台同时判断参数超限、异常趋势等，在设备预警中心处理；重要异常按规则通过唐车之家通知责任人 |
| 3D 数据驱动 | 合并实时点位并转换为对应设备／机械手状态，按 3D 约定驱动设备动画和运行数据刷新，不直接转发原始 IOT 增量报文 |
| 工时自动识别与校准 | IOT 主要识别有效加工时段和加工开始／结束，CV 主要识别台位占用；结合两者分析等待时长，并更新、校准相关工时结果 |

质量结果由第三方业务系统提供，不从 IOT 参数直接替代检验结论。台位占用时长不直接等于有效加工时长；具体关联、分析和校准规则由平台实现。

## 2. 连接与公共规则

| 配置 | 内容 |
| --- | --- |
| HTTP 服务 | `http://10.220.30.147:8368`；仅提供生产环境 |
| HTTP Header | `X-Factory-Code: BJZHLT`；`Accept: application/json` |
| HTTP Body | POST／PUT 使用 JSON；GET 无 Body；原定义无认证 |
| HTTP 成功 | HTTP 200，且 success=true、code=0 |
| MQTT Broker | `mqtt://10.220.30.147:1883`；仅提供生产环境 |
| MQTT 参数 | 3.1.1、账号密码、唯一 Client ID、QoS 0、Retain=false |
| 业务时间 | 以 IOT 报文的 `serverTime` 为依据；sourceTime 和接收时间保留用于追溯，不替代该业务基准 |

IOT 与 CV 服务器进行时间同步校准，跨源关联采用统一时区。CV 时间按接口为 UTC；IOT 时间字符串按实际环境时区解释，不将无时区字符串直接当 UTC，也不改写原始报文来伪造校准结果。

首次生产联调按配套定义落实账号、Topic 和窗口，不在生产 Topic 注入模拟值。后端持续接收与服务同生命周期，页面关闭不停止；断连后恢复订阅，不重复写推送配置。

## 3. 各接口使用方法

```text
设备／点位准备 → 核对所需推送配置 → 持续订阅实时变化
  → 解析合并，识别有效加工时段，按需查询最新值或时段历史
  → 结合 CV 台位与设备位置、MOM 产品信息建立业务关联
  → 更新分析、预警、3D 或工时结果，触发必要操作并记录结果
```

### 3.1 IF-IOT-001 获取设备清单

- **场景／策略：** 初始化、设备接入或映射变更时获取，支持人工刷新；不按秒查询。周期复核可按运维需要配置。
- **方法：** GET `/open/deviceList`，取得 data 中的 deviceCode、fundingCode、deviceName，核对 IOT 对象与平台设备、机械手及 3D 对象的关系。新增设备再查参数清单。
- **结果／异常：** 清单为空或查询失败时保留已知配置，核实后再停用设备。缺少固资号或映射冲突时标记待处理，不按名称猜映射。

### 3.2 IF-IOT-002 获取设备参数清单

- **场景／策略：** 新设备、业务所需点位变化或发现未知点位时查询；重复刷新请求合并。用参数表作参考，实际编码、类型和单位与接口结果核对。
- **方法：** POST `/open/deviceParamList`，Body 是设备码字符串数组，例如 `["cqx11"]`。批量上限未确认前先单设备查询。
- **结果／异常：** 根据 paramCode、paramName、paramType、paramUnit 解释实时 identifiers 和字符串 value；未知点位先留存原值，不用 0 代替解析失败。不同设备可能有相同参数编码，必须连同 deviceCode 识别。

**点位使用参考：** 参数表包含“正在焊接”、焊接电流／电压、送丝／打磨速度、程序、错误代码、TCP 位姿、导轨位置和轴角度等。分别用于加工状态、工艺分析、预警和 3D 数据准备；不凭名称直接固定阈值，也不把轴运动一律视为有效加工。具体判定由平台按设备业务规则实现。

### 3.3 IF-IOT-003 查询设备历史数据

**场景／策略：** 启动或重连取得最新基线；按有效加工时段查询参数用于质量关联、异常回溯和工时复核。已有完整本地数据时可复用，不用历史接口替代实时订阅。

**方法：** POST `/open/deviceHistory/getDeviceData`，填写 deviceCode，按补充开发说明区分两种模式：

| 模式 | startTime／endTime | 用途 |
| --- | --- | --- |
| LATEST | 两字段均显式为 null | 查询该设备每参数最新一条，用于初始化或恢复当前状态 |
| RANGE | 两字段均为 `yyyy-MM-dd HH:mm:ss` 字符串 | 查询指定时段的设备历史，供加工参数关联、异常分析和缺口补查 |

按有效加工起止时间组织 RANGE 查询，展开 historyData，使用 serverTime 将参数与对应产品、台位、设备和时段关联。历史 paramCode 与实时 identifiers 统一识别。历史筛选字段及边界仍须核验，不能据请求成功就认定时段数据齐全。

**分窗／异常：** 确认跨度、点数和边界后再确定拆窗；没有分页定义时不自行加参数。缺口明确标记，旧历史值不覆盖较新的实时状态。用于质量或工时分析的数据不完整时应体现缺失，不补造值或仍标记分析完成。

### 3.4 IF-IOT-004 查询推送配置

- **场景／策略：** 启动、业务点位调整前后，以及质量分析、预警或动画缺数据时只读核对；发现偏差不自动覆盖。不要求各业务模块各自高频查询。
- **方法：** GET `/open/sendConfig/list`，保存 sendFrequency 和 deviceParams，并与期望范围比较。字段表中 sendFrequency 为秒单位间隔，1 表示间隔 1 秒。
- **结果／边界：** 此接口只读配置，不建立 MQTT 订阅，也不返回设备实时值。保存配置快照和获取时间，查询完成即结束。

### 3.5 IF-IOT-005 全量更新推送配置

**场景／策略：** 为质量分析、预警、工时或 3D 补充所需点位、调整推送间隔时执行一次；不定时写入、不在每次重连时写入。该接口改变数据推送配置，不控制设备加工。

**方法：**

1. 先用 IF-IOT-004 读取并保存旧配置，结合 001／002 核验设备和点位。
2. 统一汇总各业务所需点位，生成完整目标 deviceParams 集合和 sendFrequency；不能只把某模块新增一项当全量提交，影响其他模块取数。
3. PUT `/open/sendConfig/fullUpdate`，检查 HTTP 与业务结果。
4. 再 GET 读回并观察实际消息，核验后结束。返回 data 可能只是请求回显。

**异常：** 超时先读回判断是否生效，不直接重复 PUT。覆盖、删除、空数组和共享影响范围未确认前，不做删减或空写实验。回退前核实期间无人修改，再受控恢复旧配置。

### 3.6 IF-IOT-MQTT-001 设备运行实时订阅

**场景／策略：** 后端启动后持续订阅，实时解析并驱动业务处理，不“定期订阅一次”。默认 1 Hz，可配置间隔，但每条消息只包含本次变化点位，不是全量快照；该间隔不自动保证所有业务所需的时间精度。

**Topic：** `pushToFactory/BJZHLT/device/{deviceCode}`。当前设备流编码为 cqx11、cqx12、cqx21、cqx22、dxdm、ckdm1、ckdm2、ckdm3；参数表及补充说明已覆盖 8 个编码。通配符权限未确认前逐个订阅，检查 SUBACK。

**方法：**

1. 按 UTF-8、**JSON 根数组**解析，没有外层 data；关联 Topic、接收时间和原始 Payload 供追溯。
2. 逐项校验 deviceCode、identifiers、sourceTime、serverTime、value；Topic 与报文设备不符时隔离记录。
3. 按设备＋identifiers 合并最新值，依据参数字典转换字符串 value；以 serverTime 判断业务时间及新旧，保留原始值和其他时间用于追溯。
4. 未出现的点位保持原值。例如本次只有 A 变化，不能清空 B、C；从未取得的点位保持未初始化。
5. 平台据运行点位识别有效加工开始／结束及加工时段，结合 CV、MOM 信息关联产品、台位和设备。参数记录或历史查询结果按该时段归属，供第三方质量结果关联分析。
6. 平台消费原生报警或判断超限、异常趋势，更新设备预警中心；重要异常按通知规则交唐车之家发送。持续同一异常不因每条采样重复创建预警或通知，具体规则由平台实现。
7. 按 3D 定义将设备／机械手数据转换为完整动画或运行数据消息；结合 CV 占用更新加工和等待时长等对象，再按业务规则触发后续操作。接收、解析和保存成功不等于这些业务处理已完成。

**3D 衔接：** IOT 设备码可能细分到机械手，3D 则按整机或机械手分 Topic。例如 IGM 消息可包含两个机械手，窗口打磨动画按机械手分别发送、详情按整机发送。按定义核对对象、类型、坐标和单位，不将一个 IOT Topic 直接当一个整机 Topic；IOT 采样与 3D 发布周期分别执行。字段缺失或过期不以零值、复制值或刷新发送时间掩盖。

**启动／恢复：** 按需查询 LATEST 基线或 RANGE 缺口历史，与实时流按 serverTime 合并；不因消息未携带某点位就清空该值，也不因补查成功就宣称历史完整。无消息可能表示无变化、未配置或故障，不能单凭静默判停机。设备停用或服务退出才取消订阅。

业务处理失败应保留关联与处理结果，恢复时避免重复更新或触发相同操作。服务器同步校准用于建立统一时基；加工时段和等待时长的校准由平台结合实际业务状态处理，不直接改写上游时间。

## 4. 联调步骤与完成标准

1. 核验 8 个设备流及参数字典，验证 LATEST、RANGE、实时订阅和配置读回；全量修改配置单独受控验证。
2. 验证变化点位合并、未知点位、断连恢复和历史补查，serverTime 为业务依据，IOT 与 CV 时间可对齐。
3. 选取已确认产品、台位和设备的加工实例，结合 MOM、CV 和有效加工时段取得参数，并关联第三方检验／缺陷／返修结果，验证质量分析链路可追溯。
4. 验证原生报警及平台异常规则进入设备预警中心，重要异常能按规则通知责任人，重复输入不重复产生相同业务作用。
5. 验证对应设备动画及运行数据刷新，整机／机械手映射正确，且发布频率遵守 3D 约定。
6. 验证 IOT 加工开始／结束与 CV 占用关联，平台能更新、复核加工时段和等待时长；时间偏差、缺数据和处理失败有明确结果。

**完成标准：** 接口取得的数据能进入对应业务处理，正确更新分析、预警、3D 或工时相关对象，并执行或安排必要的后续操作。可先独立验证接口，但完整业务验收需验证跨系统结果；不能止于订阅成功或历史保存。具体算法效果、预警阈值和工时判定按平台业务功能验收。

## 5. 待确认事项

| 问题 | 确认方／影响 |
| --- | --- |
| 参数查询批量上限、点位实际语义及报警码枚举 | IOT／设备方；参数表作参考，与实际返回核验 |
| 历史筛选时间是否与 serverTime 一致、区间边界、跨度、点数／分页及保留期 | IOT 方；业务基准已明确，仍需验证查询完整性 |
| fullUpdate 的覆盖／删除／空数组语义、共享范围、频率范围和生效时机 | IOT 方；决定配置变更与回退方法 |
| 实际采样与变化发送的关系、可用时间精度、静默预期、会话及通配符权限 | IOT／Broker 方；不能将默认 1 Hz 当作全部业务的精度保证 |
| 第三方质量系统的具体接入方式与关联字段 | 第三方／业务方；来源已明确，接入定义另行维护 |

预警阈值、责任人、工时推断和校准、质量分析及 3D 具体映射由平台相关业务设计与代码维护，不因本文不展开而省略业务处理。
