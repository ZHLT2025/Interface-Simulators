# MOM 接口使用说明书

分册 V1.2｜2026-10-19｜2 项接口联合使用

依据：[MOM 接口定义](../版本261017/接口定义说明书一、MOM部分-0813.md)、[生产订单增量获取适配器第一阶段核心开发说明](../../开发说明/MOM接口/IF-MOM-001与IF-MOM-002-生产订单增量获取适配器-第一阶段核心开发说明V1.md)。本文参考其中的联合调用和查询窗口方法，建议每 **10 分钟**轮询，不沿用第一阶段“仅采集保存”的范围限制。

## 1. 任务范围

- **业务目标：** 联合使用 001、002，持续获取新增或发生变化的订单工序详情，更新平台相关业务对象，并按业务规则触发后续操作。
- **接口分工：** 001 发现变化的“订单＋工序”，002 逐项获取完整详情。正常同步作为一个联合任务运行，两个接口一般不独立使用。
- **输入：** 环境、访问凭据、系统编号和上轮查询水位。
- **输出：** 更新后的订单、工序及相关业务对象，必要的后续操作，以及同步进度和处理结果。
- **说明边界：** 本文讲清接口何时调用、如何衔接及调用后的处理职责；字段映射、数据库更新、业务算法和操作触发细节由平台代码实现，不在本文展开。

“请求订单下发”在现定义中是查询详情，不是向 MOM 下达派工或设备启动指令。单接口调用可用于排查或明确的人工验证。

## 2. 连接与公共规则

| 配置 | 内容 |
| --- | --- |
| 测试服务 | `http://10.220.30.131:5000` |
| 生产服务 | `http://10.220.29.165:5000` |
| 请求 | POST，`application/json`，UTF-8，Basic Auth |
| 接口成功 | HTTP 200，且 `esbInfo.returnStatus="S"`、`esbInfo.returnCode=200` |
| 查询范围 | 001 默认 WORKCENTER=null，一次查询全部四个工位；DEVICEPN=null |
| 时间 | 按 UTC 解释，传输格式为 `yyyy-MM-dd HH:mm:ss` |
| 调度 | 建议每 10 分钟一轮；本轮未结束，不启动下一轮；接口请求串行执行 |

由后端统一执行联合任务，不由页面分别轮询两个接口。凭据从安全配置读取，不写入原始记录或日志。接口成功只表示取得有效响应，平台业务处理结果应另外记录。

## 3. 两接口联合使用方法

### 3.1 场景与完整流程

适用于首次建立订单数据基线，以及运行中根据 `LASTUPDATEON` 获取新增和发生变化的工序任务。

```text
每 10 分钟启动一轮
  → 001 按时间窗口发现变化的订单工序
  → 校验任务标识、同批去重
  → 串行调用 002 获取完整详情
  → 平台解析数据，新增或更新相关业务对象
  → 按业务规则触发必要的后续操作
  → 记录处理结果和同步进度，结束本轮
```

001 提供变化线索，002 补全详情；不另设一套独立的 002 定时轮询。原始报文保存和日志记录用于追溯、排障，不是流程终点。

### 3.2 查询窗口与水位

按参考说明暂用连续半开区间 `[STARTTIME, ENDTIME)`：

| 情况 | 查询窗口 |
| --- | --- |
| 首次运行 | ENDTIME=本轮开始时间，STARTTIME=ENDTIME−72 小时 |
| 后续运行 | STARTTIME=上轮已接受的 ENDTIME，ENDTIME=本轮开始时间 |
| 中断超过 72 小时 | 从最近 72 小时重新开始，明确记录范围外缺口 |

窗口不重叠、不增减一秒。查询水位取已接受窗口的 ENDTIME，不取列表最大 LASTUPDATEON，也不按订单逐个推进。

查询水位表示变化发现进度，不等于业务处理进度。推进水位前，应确保窗口内任务已处理完成，或已可靠登记以便继续处理，避免跳过失败项。不能仅因列表报文保存成功，就将整轮业务同步标记为完成；具体进度保存和失败恢复由平台代码实现。

### 3.3 001 发现变化，002 补全详情

1. **查询变化列表：** POST `/api/v1/get_orderlist`（IF-MOM-001）。填 UTC 起止时间、数值 SYSTEMTYPE=119，WORKCENTER 和 DEVICEPN 均为 null；每轮通常一次列表请求。
2. **识别工序任务：** 检查 `resultInfo.SYSTEMTYPE`、ORDERQUANTITY 和 MOMWIPORDERS，核对报告数与数组长度。以 `SYSTEMTYPE + WIPORDERNO + WIPORDERTYPE + OPRSEQUENCENO` 标识任务，同批重复项合并，同一订单不同工序分别处理。
3. **逐项获取详情：** POST `/api/v1/get_order`（IF-MOM-002）。SYSTEMTYPE 转为 `"119"`，当前生产订单类型使用 `"101"`；订单号和工序号从列表原样复制，保留前导零。完成一次请求后再发下一次。
4. **核对响应身份：** 检查详情返回的系统编号、订单号、订单类型及 `MOMWIPORDEROPR.OPRSEQUENCENO` 与请求一致，再交给平台业务逻辑处理。标识不匹配时不能更新对应业务对象。
5. **执行平台业务处理：** 解析完整详情，新增或更新订单、工序及相关关联对象；根据实际变化，按业务规则触发相关状态重算、展示更新或其他必要操作。具体处理由平台代码实现，不能止于保存响应。
6. **汇总结果：** 分别记录接口获取结果、业务处理结果和失败项，按 3.2 管理进度。成功空列表无需调用 002，也不能据此删除已有订单。

公共响应还需满足内容完整、可按 UTF-8 解析为 JSON Object，且 esbInfo、resultInfo 及成功字段有效。状态、时间和其他业务字段的解释与使用，由平台按已确认规则处理。

### 3.4 异常与追溯

| 情况 | 处理原则 |
| --- | --- |
| 001 调用或响应无效 | 记录失败，不将该窗口视为已接受，恢复后继续查询 |
| 列表数量不一致或元素无效 | 记录差异，处理可识别任务，保留异常以便核查，不静默跳过 |
| 单个 002 调用失败或身份不匹配 | 记录具体任务，其他任务可继续；失败项须可恢复处理 |
| 数据已取得，但平台解析或更新失败 | 单独记录业务处理失败，不能标成同步完成；保留数据及任务关联供恢复 |
| 重复执行或失败重办 | 平台应避免重复创建业务对象和重复触发相同操作 |

至少保留查询窗口、任务标识、调用结果、业务处理结果及错误。原始响应可保存用于追溯；是否采用 RAW、MANIFEST 及其文件格式，由实现方案确定。重试次数、补偿机制和对象更新方式不在本册规定。

## 4. 联调步骤与完成标准

1. 用首次 72 小时窗口、WORKCENTER=null 跑通“001→002→平台解析→业务对象更新→必要的后续操作”。
2. 再执行一轮增量，核验新增及变化的工序能正确处理，窗口连续，建议轮询间隔为 10 分钟，无轮次重叠。
3. 验证同单多工序、同批重复、数量异常、空列表，以及接口失败和平台处理失败的区分。
4. 验证重启续办、失败任务不遗漏、重复执行不重复建对象或触发相同操作；中断超出查询范围时有缺口记录。

**完成标准：** 接口能联合取得所需详情，平台能完成对应业务对象更新，并按业务规则执行或安排必要的后续操作，处理结果可追溯。仅 HTTP 成功、响应校验通过或原始文件保存成功，不代表业务闭环完成。具体业务效果按平台相关功能验收。
