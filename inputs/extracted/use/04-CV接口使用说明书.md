# CV 接口使用说明书

分册 V1.1｜2026-10-19｜1 项接口、13 类事件

配套定义：[CV 接口定义](../版本261017/接口定义说明书四、CV部分-1013.md)。完整报文查配套定义；本文标为“建议”的处理流程为实施建议，协议冲突见第 5 节。

## 1. 任务范围

- **本平台角色：** 提供 HTTP 接收服务；视觉算法产生事件后主动请求平台。
- **业务目标：** 接收有效视觉事件，解析事件内容、关联现场业务对象、更新相关状态，并按业务规则触发必要的后续操作，形成完整闭环。
- **输入：** 算法事件、证据引用、摄像机／ROI 与现场对象映射。
- **输出：** 更新后的相关业务对象及状态、必要的后续操作，以及事件接收和业务处理结果。
- **说明边界：** 算法方负责检测和上报，平台负责接收及业务处理。本文重点说明触发时机、调用方法、关键字段和响应判断；状态推断、对象更新、存储及调度细节由平台代码实现，不在本文展开。

## 3. 各接口使用方法

### 3.1 IF-CV-001 接收与处理

**场景／策略：** 算法确认一次业务事件后上报，平台根据事件更新相关业务对象并触发后续操作。一次事件不因持续观测或网络重发而重复产生业务作用。

```text
算法确认事件并上报
  → 平台接收、校验和重复识别
  → 解析事件，关联区域、台位、设备或产品等业务对象
  → 按业务规则更新状态并触发必要的后续操作
  → 记录接收及处理结果，异常可追溯、可恢复
```

原始事件和证据记录用于追溯，不是流程终点。接口响应按第 2 节约定返回，不要求等待全部后续操作结束后才响应。

**方法：**

1. 校验公共字段：spec_version="2.0"、algorithm_version="1.0.0"；event_definition 按 `{event_type}-{roi.id}` 组成。
2. event_id 保存为字符串；timestamp 是发生时间，sent_at 是发送时间，两者使用 UTC 毫秒 ISO 8601。另记接收时间。
3. 按 event_id 识别重复。同一创建事件的相同内容重试不重复产生业务数据或操作；同 ID 不同内容记录冲突，不静默覆盖。
4. 可靠接收事件，并按已确认的成功格式响应；保留事件标识、证据引用和处理结果供追溯，具体保存方式由平台实现。
5. 解析事件内容，按 ROI／摄像机等映射关联业务对象，再结合已有业务状态更新相关对象；映射缺失或处理失败时记录具体原因，不猜对象或标记处理完成。
6. 根据实际业务变化，按规则触发 3D 更新、通知或其他必要操作，不要求每条事件都触发所有操作。具体状态推断与操作逻辑由平台代码实现。

**字段要点：** PERSON_COUNT 使用 count；WALL_FLIP 使用 wall_state、state_sequence；其他类型不传这些专属字段。targets 可以按定义为空，证据文件引用需对应；图片读取和保存方式由平台实现。

### 3.2 事件的使用场景

右列保留各类事件的业务用途，具体判断规则不在本册展开。车辆进出用途适用于已确认的车辆类别和 ROI 场景，不能仅凭通用事件类型确定是哪一类车辆；对应关系由算法、平台和业务方确认。

| event_type | 场景与处理 |
| --- | --- |
| ENTER | 目标进入 ROI，结合区域和目标类别更新相关业务状态 |
| LEAVE | 目标离开 ROI，结合已有状态处理离开及相关业务变化 |
| WALL_FLIP | 更新已关联侧墙的水平／竖直姿态；不据此猜正反面 |
| PERSON_COUNT | 更新区域人数，可触发人员 3D 消息；0 人是有效值，多 ROI 不重复计数 |
| SPARK | 结合焊接观测信号、设备和工序状态，更新相关业务状态 |
| TRANSFER_VEHICLE_EMPTY | 更新空载观测，不等于一次新进厂／出厂 |
| EMPTY_TRANSFER_VEHICLE_ENTER | 成品转运车空车进入指定区域，可触发成品转运车进厂动画 |
| EMPTY_TRANSFER_VEHICLE_LEAVE | 型材进料车空车离开，可触发原料车离厂动画 |
| LOADED_TRANSFER_VEHICLE_ENTER | 型材进料车进入，可触发原料车进厂动画 |
| LOADED_TRANSFER_VEHICLE_LEAVE | 成品转运车离开，触发成品转运车离厂动画 |
| SIDEWALL_FINISHED_PRODUCT_ENTER_TRANSFER_VEHICLE | 更新成品装车相关状态；出厂动画具体节点另行确认 |
| PROFILE_LIFTED_FROM_TRANSFER_VEHICLE | 更新型材从进料车吊离后的相关状态，可触发型材模型显示状态切换 |
| SOUNDPROOF_COVER_MOVE_COMPLETED | 隔音罩切换工位并到位，结合已有状态更新相关台位、工序或设备状态 |

### 3.3 隔音罩移动完成

- 仅在固定两个既有工位 ROI 之间切换并到位时上报一次。静止、移动中、工位内位移、启动时首次看见静止罩体均不触发。
- roi.id 是到达工位；另一配对工位为来源。不新增来源／目标 ROI 或方向字段，event_data 沿用 targets。
- timestamp 是确认到位时间，不直接等于机床开始加工时间。
- 平台结合源台位、目标台位等已有业务状态，更新相关台位、工序或设备状态，并按规则触发后续操作；具体加工开始／完成等判断由平台业务逻辑实现，本册不规定推断算法。

### 3.4 重试与恢复

- 调用方遇 500 或网络失败，复用原 event_id；成功后停止重发。401 修复凭据，422 修复字段。
- 建议有限退避重试，具体次数和幂等保留期由双方确认。
- 事件已成功接收后，平台内部处理或后续操作失败由平台负责恢复，不要求算法重新创建事件。具体重试、补偿和调度方式由平台实现。
- 接口接收失败与业务处理失败分别记录；业务处理失败不能标记为闭环完成。恢复或重复处理应避免重复更新和重复触发相同操作，旧事件不直接覆盖新状态。
- 修订／撤销尚缺完整规则。确认事件关联、版本和回滚前，不宣称这两类操作已完成业务处理。

## 4. 联调步骤与完成标准

1. 确认请求、响应格式及成功响应的含义，跑通“算法上报→平台接收→业务对象更新→必要的后续操作”。
2. 重发同一 event_id，确认不重复产生业务结果或操作；验证字段错误、网络重试，以及接收成功后平台处理失败的恢复。
3. 逐类验证 13 种事件及条件字段，核验 ROI／车辆类别映射、零人数处理，以及对应业务状态和后续操作。
4. 验证罩体静止不发事件、工位切换到位只发一次；平台依据已确认的业务规则更新相关状态，不能将到位时间直接当作加工开始时间。

**完成标准：** 事件能正确上报和接收，平台能完成对应业务对象及状态更新，按规则执行或安排必要的后续操作，结果可追溯。HTTP 成功、事件保存或证据记录完成，不代表业务闭环完成；具体业务效果按相关平台功能验收。可先使用测试消费者独立验证接口，再完成实际业务集成。

## 5. 待确认事项

| 问题 | 确认方／影响 |
| --- | --- |
| Basic Auth 是否最终方案；成功是 returnStatus／returnCode 还是旧备注 status=ok；成功响应具体承诺什么 | 平台／算法方；统一格式与接收确认含义，不混用 |
| 当前字段表 cid 为 Number，旧记录写整数数组 | 双方；明确有效 schema |
| 当前 evidence 为单图对象，旧变更记录允许 null | 双方；明确证据必填规则 |
| 修订／撤销的关联、ID、顺序与业务回滚；重试及幂等保留期 | 双方；决定重复与更正处理 |
| ROI 配对、车辆类别与事件用途对应关系、检测稳定阈值及区域计数口径 | 算法／业务方；明确有效事件和适用业务场景 |

平台侧的状态推断、对象映射与更新、存储及后续操作规则，由相关业务设计和代码实现另行维护。
